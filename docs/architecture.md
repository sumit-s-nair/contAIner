# contAIner Architecture

This document describes the core architecture of the contAIner system, a four-stage agentic pipeline designed to safely setup, diagnose, and manage software projects.

## Pipeline Overview (Systems 1-4)

The architecture is divided into four distinct sub-systems, each responsible for a specific phase of execution:

1. **System 1 (Intent Analysis & NER)**: Analyzes user input and extracts intent alongside Named Entities (e.g., target dependencies, ecosystem, requested tools).
2. **System 2 (Planner)**: Generates a high-level sequence of abstract `PlannedStep` actions (e.g., `ISOLATE`, `INSTALL`, `DETECT`). It relies on canonical Workflow Templates which enforce hard ordering constraints.
3. **System 3 (Command Generation)**: Translates the abstract `PlannedStep` actions from System 2 into concrete shell commands represented as `AtomicStep`s.
4. **System 4 (Sandboxed Execution)**: Executes the concrete commands in a secure environment. It strictly enforces a three-tier risk classification gate (SAFE, REVIEW, BLOCKED).

## Data Contracts & Canonical Templates

The interaction between the systems is strongly typed:

- **RepoManifest**: Generated by the `repo_scan` module, this captures the state of the repository, including ecosystems, dependencies, and discovered conflicts. System 2 uses this to branch its logic.
- **WorkflowTemplate**: System 2's templates encode constraints as a DAG. For example, `setup_project` enforces that an `ISOLATE` action MUST precede `INSTALL` if `RepoManifest.conflicts` is non-empty.
- **PlannedStep**: The output of System 2. A structured intent (e.g., `ActionType.INSTALL`) independent of shell syntax.
- **AtomicStep**: The output of System 3. Contains the exact `command`, `description`, and a `destructive` flag.

## `repo_scan` Logic

The `repo_scan` module provides the ground-truth environment state used by System 2. It parses project files (e.g., `package.json`, `requirements.txt`) to build the `RepoManifest`. Crucially, it implements conflict detection (e.g., identifying when a user attempts to globally install dependencies that conflict with system packages or other projects) which triggers isolated environment workflows (e.g., virtual environments).

## Safety Gate & Risk Classification

System 4 acts as the ultimate gatekeeper, evaluating each `AtomicStep` through the `CommandRiskClassifier`. It implements a strict three-pass hierarchy:

1. **BLOCKED**: Hard denylist via regex. Matches catastrophic actions (e.g., `rm -rf /`, fork bombs) or out-of-scope filesystem writes. Execution is unconditionally halted.
2. **REVIEW**: Requires user confirmation. Triggered by destructive actions (e.g., `rm`, `git reset`, `sudo`), planner-flagged destructive steps, or the `--force` flag when paired with a high-risk verb.
3. **SAFE**: Known-safe action allowlist (e.g., package manager installs without destructive context, `ls`, `cat`). Unknown commands default to REVIEW as a fail-safe mechanism.

By default, the executor halts on BLOCKED or unconfirmed REVIEW steps (`halt_on_blocked=True`).

## Recovery State Machines

When execution fails or is BLOCKED, the system transitions into a recovery state machine:
- It generates detailed training signals back to System 2/3 (e.g., "Ordering violation: 'check' must occur before 'install'").
- System 3 can be prompted to regenerate the command without destructive flags, or System 2 can replan an alternative path (e.g., using a fallback action like `ESCALATE`).
- In extreme cases, execution falls back to manual user intervention.


## Tracked Open Items
- **System 3 Stub**: System 2 RL training currently uses a deterministic command-expansion stub (src/rl_env/system3_stub.py) in place of System 3. Swapping in the real trained System 3 model is a required follow-up before this pipeline reflects the intended architecture.
- **Main Env Advancement**: Advancing the main environment with the best-of-G action accelerates convergence but biases exploration off-policy. This design decision is worth revisiting if exploration diversity becomes an issue later.
